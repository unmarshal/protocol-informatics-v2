# MCP stdio server

`protocol-informatics-v2 mcp-stdio <investigation-dir>` exposes one existing investigation to an MCP client. Create the investigation with `init` first, then point the client's stdio server configuration at the compiled binary and that directory. The process reads JSON-RPC from standard input and writes protocol messages to standard output; diagnostics use standard error. The server uses the MCP 2025-11-25 initialization protocol through the official Rust SDK.

For example, after `cargo build --release`:

```json
{
  "command": "/absolute/path/to/protocol-informatics-v2/target/release/protocol-informatics-v2",
  "args": ["mcp-stdio", "/absolute/path/to/investigation"]
}
```

The directory is fixed for the lifetime of that server process. Each tool call reloads the current event-sourced investigation. Read tools return structured JSON plus text content and preserve the same IDs, revision, limits, and evidence coordinates as the CLI. Tool failures return MCP tool errors with the underlying validation message. A client can connect multiple investigations by configuring separate server processes.

## Agent workflow

1. Call `summary`, then page `experiments`, `trials`, `hypotheses`, `decisions`, and `search_observations` to narrow the evidence. Check `revision` between pages and follow `next_offset` until it is absent.
2. Call `span` to inspect exact message bytes and original source offsets. Use `pair_exchanges` and `cluster` for provisional patterns; use `validate_exchanges` and `validate_clusters` on separate trials to find counterexamples.
3. Call `create_hypothesis`, `create_experiment`, and `create_trial` to record a claim, falsifiable question, and controlled condition. These creation calls have no retry key, so inspect `hypotheses`, `experiments`, or `trials` before repeating an uncertain call.
4. Use `capture_step` with a stable `step_key` to record an action, run a bounded local command that emits a supported capture format, import its bytes, and tag every resulting observation to that capture scope. The command is an argument array, without an inserted shell. It executes with the server process's user privileges. `mark_action`, `capture_start`, `capture_status`, `capture_stop`, and `tag_capture` support separate action and live capture timing.
5. The `capture_step` result gives the capture ID, observation count, up to 20 observation IDs, and compact tag-page records. Retrieve the remaining observations with `search_observations` filtered by `capture_id`.
6. Use `annotate_value` to record externally known unsigned values in discovery and validation observations, then `infer_value` for exact candidate offsets. `infer_framing`, `infer_tlv`, `infer_varint`, `infer_delimiter`, and `infer_checksum` test other bounded models across controlled trials. `probe_framing`, `probe_tlv`, and `probe_varint` inspect proposed records. Commit complete fixed-width, unsigned LEB128, or delimiter models with `commit_framing`, `commit_varint`, or `commit_delimiter` and a stable retry key; paged `frame_runs` discovers committed interpretations by trial and model, while `frame_run_status`, paged `frames`, and `frame_span` revisit exact derived records. `cluster_frames` groups logical bytes from committed frames of one model. `validate_frame_clusters` checks those provisional groups against committed frames in a distinct trial, returning inspectable frame IDs and counterexamples. `align_frame_cluster` returns bounded, gap-aware alignment columns and frame IDs for one group. `annotate_frame_value` and `infer_frame_value` test controlled fields inside those records. `review_trials` combines one discovery/validation pair into bounded model checks, grouping counterexamples, and suggested next tool actions. `evaluate_hypothesis` records an **agent or analyst supplied rating**, not a computed probability. Finish with `record_decision` and `verify`. Value annotations, evaluation, and decision writes have no retry key; inspect the record pages before repeating an uncertain call.

Capture commands have the CLI's 1–600000 ms timeout and 32 MiB output limit. A capture-scope tag says that an observation came from the captured step; it does not assert that the observation is a reply. The keyed operations are retry-safe according to the [capture step workflow](capture-step.md). The MCP server delegates writes to the same CLI operations, so the append-only event log and artifact verification remain authoritative. `cluster_frames` accepts optional `run_keys` to choose one committed interpretation per observation when competing runs exist; without that selection, it rejects overlaps rather than double counting.

The server currently exposes 47 tools: `summary`, `experiments`, `trials`, `hypotheses`, `decisions`, `search_observations`, `span`, `pair_exchanges`, `validate_exchanges`, `cluster`, `cluster_frames`, `align_frame_cluster`, `validate_clusters`, `validate_frame_clusters`, `infer_value`, `infer_framing`, `infer_tlv`, `infer_varint`, `probe_delimiter`, `infer_delimiter`, `review_trials`, `probe_framing`, `probe_tlv`, `probe_varint`, `commit_framing`, `commit_varint`, `commit_delimiter`, `frame_run_status`, `frame_runs`, `frames`, `frame_span`, `annotate_frame_value`, `infer_frame_value`, `infer_checksum`, `verify`, `create_experiment`, `create_trial`, `create_hypothesis`, `evaluate_hypothesis`, `annotate_value`, `record_decision`, `mark_action`, `capture_step`, `capture_start`, `capture_status`, `capture_stop`, and `tag_capture`. The JSON CLI provides report generation. A delimiter commit preserves a structural interpretation; it does not certify the protocol grammar.
