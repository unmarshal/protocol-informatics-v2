# Conservative message grouping

The current `cluster` command proposes **format groups**, not semantic message types. It exposes the observations and rule behind every group so an agent can inspect or challenge the split before aligning messages within it.

1. If requested, partition by the exact observed direction string. This is a useful capture prior, but can over-separate traffic from different host pairs. `ignore` removes it.
2. Within each group, consider low-cardinality bytes in the first 16 message bytes. A candidate needs 2–4 values, at least three observations per value, and another stable byte at least four positions away or a distinct, stable message length in each child. This avoids treating adjacent bytes of a multibyte identifier as independent proof of separate formats.
3. Repeat up to four levels, with at most 32 groups. Return all sampled member IDs, the discriminator path, constant header bytes, a medoid representative, and the three farthest members. Similarity compares at most the first 256 bytes plus a length difference. At most 512 observations enter the clustering calculation.

For larger selections, the tool groups observations by direction and exact byte length, gives every stratum one slot, allocates remaining slots roughly in proportion to stratum size, then chooses members by a stable SHA-256 rank of observation ID. This avoids the periodic bias of taking every nth packet from an alternating request/reply trace. If there are more than 512 strata, it uses a global hash sample. The response states the number selected, the number analyzed, the sampling method, and the stratum count. Group member counts and stable bytes describe **the analyzed sample**, not all selected traffic. A rare format can still be missed; inspect unsampled observations or repeat with a different capture when that matters.

The method deliberately favors **unassigned ambiguity over false precision**. An adjacent opcode and flag may be a real type distinction that this first rule misses. A counter, identifier, checksum, or correlated length may still cause a misleading split. The `respect` and `ignore` modes, split evidence, representative, and farthest members let an agent investigate such cases.

## Held-out check

`validate-clusters` learns groups only from a discovery trial, then checks observations in a distinct validation trial of the same experiment. A held-out observation is compatible with a group only if the group has at least three discovery members, **at least one stable header byte**, a matching direction rule, and every reported stable byte in the group's first 16 bytes present and equal. A group with no stable header evidence abstains instead of assigning every held-out message. Compatible groups are ranked by distance to their medoid, using at most 256 bytes plus a length difference. A unique compatible group is assigned; close top distances (within 0.05) remain ambiguous. When none fit, the result lists rejected groups and whether sample size, stable evidence, direction, or exact stable-byte offsets failed.

Discovery clustering analyzes at most 512 observations using the disclosed sampling rule. Validation evaluates **all** held-out observations when the trial has at most 10,000. Larger validation trials use a disclosed 512-observation sample, so their counts are not full-trial counts. The JSON result returns at most 512 detailed validation rows while retaining exact evaluated counts. Unassigned rows take priority, then ambiguous rows, then a stable hash selection of assigned rows; all returned rows retain the source order. It reports how many details were omitted and how many counterexamples were returned. Each row lists at most five compatible or rejected groups. A zero counterexample count is evidence only over the evaluated observations and the sampled discovery model.

An assignment tests whether a structural fingerprint generalizes; it is not a known message-type label or an accuracy measurement. A newly varied counter can make a previously stable byte fail, and a new message kind may correctly stay unassigned. Inspect the counterexamples, repeat with independent captures, and use intervention outcomes or request/response relations before promoting a group to a semantic type claim.

## Committed record grouping

`cluster-frames` applies the same conservative split rules to logical bytes of committed fixed-width, unsigned LEB128, or delimiter frames. It analyzes one model at a time and returns frame IDs. `validate-frame-clusters` learns those groups from committed frames in one trial and checks committed frames in a distinct trial of the same experiment. The result identifies assigned, ambiguous, and unassigned **frame IDs**, with compatible groups and stable-byte rejection offsets. It retains the 512-frame discovery cap, 10,000-frame full validation limit, and counterexample-first 512-row detail limit above. Counts cover only committed frames selected for those trials; an uncommitted capture is outside the check.

Both commands reject overlapping interpretations of one observation. Supply explicit run keys when multiple committed runs of the chosen model cover that observation, selecting one run per observation. Trial and run-key filters are reported in the result. Revisit any frame with `frame-span`, then vary the capture condition and repeat the held-out check before treating a group as a protocol type.

`align-frame-cluster` compares logical bytes inside one returned frame group. Its result maps every alignment row to a stable frame ID and names the reference frame. Up to 32 frames enter one alignment; when a group is larger, it keeps the representative and three farthest sampled members, then fills remaining slots by a stable hash rank. The result discloses selected and aligned counts and the sampling method. Each frame must have 1–4096 logical bytes, and the estimated total pairwise work may not exceed 25 million cells. These bounds prevent an agent request from creating an unbounded alignment or tool response. The columns are descriptive statistics, not inferred field boundaries; use `frame-span` and controlled trials to test candidate meanings.

This is a small, original heuristic informed by [Discoverer's format distinguishers](https://www.usenix.org/conference/16th-usenix-security-symposium/presentation/discoverer-automatic-protocol-reverse-enginee) and [NetPlier's emphasis on uncertain type fields](https://www.ndss-symposium.org/wp-content/uploads/ndss2021_4A-5_24531_paper.pdf). It does not implement either paper's full algorithm.
